# M4 Key 池运营（总览）

- **状态**：方向已定（2026-11-13 用户同意「Key 池运营」作为 M4），各卡规格待逐张审批。
- **约束**：不改内核（`internal/core`）与契约（`internal/protocol`）的导出 API，不改分层规则与 adaptertest 套件，不加依赖。

## 1. 为什么做

网关的主要用法是：注册程序批量开免费账号，拿到几十上百把 Key，交给网关统一调度，再给 AI 调用。2026-11-12 导入 270 把真实 Key（Bivia 97、Tavily 86、MinerU 87）的实测暴露了 Key 生命周期上的缺口：

| 现象 | 现状 | 后果 |
|:--|:--|:--|
| MinerU 账号有过期时间 | 上游 Key 只有权重、并发上限、状态三个字段 | 要靠转换脚本手工过滤；过期 Key 仍被选中，失败一次才隔离 |
| Tavily 每月额度、MinerU 每日额度 | 调度器不知道额度 | 每把 Key 用满后都要先失败一次才冷却 |
| 注册程序持续产出新账号 | `keys import` 是一次性手工命令 | 要记得重新导入；账号失效后 Key 留在库里 |
| 池还剩多少容量 | 没有汇总 | 池快空了没人知道，只能等 503 |

## 2. 卡片与依赖

```
T61（独立，可随时穿插）
T62 Key 元数据 ──► T63 按额度调度 ──► T65 Key 视图
              └──► T64 补充与告警
```

| 卡 | 交付 | 用户可见的变化 |
|:--|:--|:--|
| T61 | Linux `-race` 全量测试（沿用 T46 步骤）；24 小时稳定性测试并记录内存、goroutine、延迟基线；`gateway backup` / `gateway restore`（SQLite 在线备份 + 主密钥提示） | T55 ~ T60 的并发代码有了竞态检测结果；可以安全迁移机器 |
| T62 | Key 增加 `expires_at` 与 `label`；导入命令从文件字段读取；过期 Key 不参与调度 | 不再需要手工转换脚本过滤过期账号 |
| T63 | 池级额度声明（单位、上限、周期、重置时区）；每 Key 周期用量计数（启动时从计费事件恢复）；用满主动冷却到重置时刻；`drain`（用完一把再换）/ `spread`（平均分摊）两种策略 | Key 用满后不再失败一次才冷却 |
| T64 | `gateway keys sync`：按文件同步，新增导入、元数据更新、文件中消失的 Key 停用；池可用 Key 或剩余额度低于阈值时告警（Prometheus 指标、管理面 MCP、Web UI 横幅） | 注册程序直接给网关补 Key；池快空时能提前知道 |
| T65 | Web UI 与管理面 MCP：每 Key 的周期用量、剩余额度、失败率、过期时间；每池剩余容量与预计耗尽时间 | 可以直接问 AI「Tavily 池这个月还够用吗」 |

## 3. 不在 M4 范围

- 更多适配器：已有 add-api skill 与通用 REST 转发，按需接入，不设专门里程碑。
- 编程 Agent 兼容（WebSocket Responses 等）：需要先收集失败样本。
- 多实例、PostgreSQL、对外服务：单机够用之前不做。
- 主动探测上游余额：各家没有统一的余额接口；T63 用网关自己的计量推算，T64 可以为个别上游加探测，届时单独审批。
