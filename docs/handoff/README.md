## 2. 审批门（重要）

T42、T43、T45 都包含 `spec/` 的修改。AGENTS.md §4 规定：除 `DONE` 状态外，spec 的任何修改都要用户同意。因此这三张卡分**两个阶段**：

1. **阶段 A：规格**。把卡里「§3 规格草案」整理进对应的 `spec/` 文件（只改 spec，不写代码），单独提交，交给用户审批。草案里标了「待定」的地方要列出来，请用户逐条回答。
2. **阶段 B：实现**。用户回复同意之后才开始写代码。用户改了草案的，以用户的版本为准。

阶段 A 没批就开始写代码，整张卡返工。

## 3. 统一的交付要求

### 3.1 分支与提交

- 每张卡在自己的分支上做：`task/t40-race-ci`、`task/t41-real-clients` 这种格式，基于最新的 `main`。
- **不要推送到 `main`，不要合并，不要改写历史**（不用 `rebase`、`commit --amend`、`reset --hard`）。做完把分支推到远端，或者把分支名告诉用户，由审查方合并。
- 提交信息格式见 AGENTS.md §6：`类型(范围): T4x 一句话说明`，结尾加执行者自己的署名行（如果有）。
- 阶段 A（规格）和阶段 B（实现）是两个提交。阶段 B 可以按卡里的「建议提交拆分」拆成多个提交。

### 3.2 交付说明

完成后按 AGENTS.md §5 的格式写交付说明，**另外必须包含**：

- `go run ./tools/check` 最后 10 行输出的原文。
- 卡里「验收标准」逐条写「满足 / 不满足 + 原因」。
- 改动文件超出卡里「涉及文件」的，逐个说明理由。
- 新增的每一处 `SPEC-GAP(T4x)`：位置、选择了什么行为、为什么。

### 3.3 本机环境提示

- 本仓库的开发机是 Windows，内存较小。完整检查建议这样跑：
  ```bash
  GOFLAGS=-p=2 GOMAXPROCS=2 go run ./tools/check
  ```
- Windows 上没有 C 编译器时，`-race` 会被自动跳过（检查脚本会打印 note）。**需要竞态检测的卡（T40）必须在 Linux 上跑**。
- 用 Python 或 Bash heredoc 生成 Go 源码时，`\n` 很容易被转义成真实的换行，导致字符串字面量断开。改 Go 文件请用编辑器或 Edit 类工具。

## 4. 审查方怎么验收（你可以提前自查）

每张卡我都会做以下检查，任一不过就退回：

1. 在你的分支上重新跑 `go run ./tools/check`；T40 合入之后，还会再跑一次 `go test -race ./...`。
2. `git diff main...<你的分支> --stat`：确认改动范围与卡一致，没有顺手改别的。
3. 已有测试的**期望值没有被修改**。黄金文件（`internal/translate/testdata/**/expected.*`）只允许在卡里明确说可以改的地方改，而且每处改动要在交付说明里解释。
4. 逐条核对卡里的验收标准。
5. 看代码：错误有没有被忽略，读取有没有上限，日志和错误里有没有凭据明文，有没有往内核或契约里加协议知识。
6. 用户审批过的规格与实现是否一致。

## 5. 不要做的事

- 不要修改 `internal/core` 与 `internal/protocol` 的导出 API（spec/13 §7）。如果某张卡看起来必须改，停下来报告。
- 不要修改 `internal/archtest` 的规则或 `internal/adapter/adaptertest` 套件。新增包需要放进分层规则时，先报告，由用户决定。
- 不要新增第三方依赖。T45 的 Prometheus 文本格式要手写，不能引入 `prometheus/client_golang`。
- 不要提交任何真实的上游 API Key、客户端 Token、客户端的提示词或代码内容（T41 尤其注意）。
